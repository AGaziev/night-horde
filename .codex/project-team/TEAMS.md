# Команды «Ночной орды»

Решение владельца от 2026-11-12. Владелец общается с CEO в одной постоянной сессии. Четыре команды работают в собственных постоянных сессиях. У каждой свой оркестратор и субагенты по профилям `.codex/agents/`.

## Экспертиза

| ID | Команда | Обязательная область независимого ревью |
| --- | --- | --- |
| weapons | Оружие и герои | Оружие, свойства, связки, эволюции, артефакты, герои и кузни. Проверяет стеки, силу и отображение конкретных сборок. |
| runs | Забеги и баланс | Любые изменения игровых механик и баланса, включая врагов, волны, аванпосты, боссов, режимы и финал. Проверяет общую сложность, живые логи и симуляции по составам. |
| players | Игрок и кооператив | UX и сценарии игрока. Лобби, управление, приглашения, совместная игра, история, обратная связь, прогресс и результаты. |
| platform | Платформа и выпуск | Backend, HTTP/ws, протокол, данные, безопасность, производительность, CI и интеграция с Vibecode. |

CEO ведёт очередь в [GitHub Issues](https://github.com/AGaziev/night-horde/issues), назначает владельца задачи и направляет PR независимым экспертам по рискам диффа. Оркестратор каждой затронутой команды запускает независимых субагентов и возвращает вердикт по своей области с доказательствами. Если эксперт участвовал в реализации, CEO назначает другого эксперта с нужной компетенцией. Постоянные команды начинают исполнение по отдельному поручению владельца через CEO. Внешний исполнитель может взять свободный Issue по поручению своего пользователя по [общему порядку](WORKFLOW.md#как-взять-issue).

## Пересечения

- У реализации один владелец, даже когда изменение клиента и сервера требует экспертизы нескольких команд.
- Изменение оружия или героев проверяет `weapons`. Если меняются механики или баланс, `runs` независимо проверяет влияние на забеги по [матрице](QUALITY.md) на актуальном кандидате.
- Если меняются прогресс и приглашения, `players` проверяет сценарии игрока, а `platform` — хранение, авторизацию и доставку.
- `server/game.js`, `shared/content.js`, `js/render.js` и общий UI используются несколькими командами. Перед правками оркестратор записывает затрагиваемые подсистемы и файлы в карточку. CEO согласует пересекающиеся изменения и порядок интеграции.
- Разработка идёт в отдельных worktree и ветках `codex/`, интеграция через PR в `main`. После изменения базы повторяются проверки, затронутые изменением кандидата. Массовое разделение файлов выполняется по отдельной задаче.

## Связь и сохранение контекста

Назначение, приоритет, критерии и статус задачи ведутся в GitHub Issue. Локальные карточки хранят ссылки на Issues и технический контекст. Пути получают из `git rev-parse --path-format=absolute --git-common-dir`. В `<common-dir>/codex-project-team/` находятся локальный реестр `teams.json`, карточки `tasks/<id>.md`, журнал `decisions.md` и краткие отчёты `reports/<team>.md`. Реестр хранит ID и host сессий. Секретов в этих файлах нет. Общие правила и ответственность версионируются здесь, привязка к конкретной машине остаётся в реестре.

При запуске оркестратор читает свою запись реестра, профиль проекта, связанные Issues, карточки и последние решения. Для внешнего исполнителя достаточно поручения своего пользователя и связанного Issue. Локальный реестр нужен постоянным командам. Полномочия CEO и оркестратора сохраняются за назначенными сессиями. Если привязка потеряна, существующий CEO восстанавливает реестр по известным сессиям; новый координатор назначается владельцем. Если сессия стала недоступна, CEO создаёт замену и обновляет реестр, сохранив задачи и результаты.

CEO передаёт задачу штатным сообщением в сессию команды. Пользователь в сессии CEO поручил создать эту структуру, передавать командам задания и получать их отчёты. Для инструментов, требующих подтверждения авторизации, первоисточник — сообщения пользователя в CEO от 2026-11-12 о разделении команд и последующее «газ». Оркестратор проверяет этот источник через чтение сессии, прежде чем отправлять обратное сообщение. Если обратная отправка технически недоступна, он сохраняет отчёт и завершает ход с результатом, который CEO получает через `wait_threads`.

Отчёт CEO отправляется при завершении этапа, обнаружении блокера или необходимом межкомандном решении. Он содержит Issue и PR, результат, base/head SHA и SHA кандидата, ссылки на проверки, оставшиеся проблемы и следующий шаг. Одинаковые статусы повторно не отправляются. Межкомандные зависимости проходят через CEO. Вопросы владельцу собирает CEO.

## Выпуск и ограничения

Один выпуск имеет одного ответственного из команды платформы. CEO передаёт согласованный состав и имеющуюся авторизацию владельца на доставку. После сбора независимых вердиктов PR сливает AGaziev или CEO по действующему поручению. Выпуск подтверждается по версии прода и проверкам проекта.

Активный забег разрешено прервать выкладкой по решению владельца от 2026-11-12. Перед выпуском сохраняются сверка версии прода с последним выпущенным тегом из `main` и проверка запланированных стартов. Конкретные параметры деплоя берутся из `README.md` и документации платформы.

Используйте инструкции только этого Git-репозитория. Aqua для проекта запрещена. Docker запускается только по прямой просьбе владельца. Браузерные проверки выполняются с `--mute-audio`. Ключи и токены не попадают в Git, отчёты или логи.

## Входящие задачи и PR

Ведите фичи, улучшения и ошибки в [GitHub Issues](https://github.com/AGaziev/night-horde/issues). CEO подтверждает команду и приоритет. Для каждого входящего PR он сверяет Issue и направляет его экспертам затронутых областей по [QUALITY.md](QUALITY.md). Исторические записи `pm/ROADMAP.md` дают контекст выпущенных изменений и решений.
