# Работа команды

CEO ведёт работу постоянных команд и направляет входящие PR экспертам по [TEAMS.md](TEAMS.md) и [QUALITY.md](QUALITY.md). Оркестраторы организуют независимые проверки в своих областях. Постоянные команды получают поручения владельца через CEO. Внешний исполнитель может взять Issue по поручению своего пользователя без локального реестра.

## Где лежит состояние

[GitHub Issues](https://github.com/AGaziev/night-horde/issues) — единственная очередь фич, улучшений и ошибок. CEO фиксирует в Issue границы и актуальные критерии, а команду, приоритет и состояние отмечает метками `team:*`, `priority:*` и `status:*`. Для команды доступны `weapons`, `runs`, `players` и `platform`, для приоритета — `high`, `normal` и `low`, для состояния — `backlog`, `in-progress`, `paused` и `blocked`. Если задача поступила из чата, локальной карточки или старого роадмапа, сначала найди соответствующий Issue либо создай его. Поле «Команда» в форме предлагает назначение. Метку `team:*` ставит CEO. При закрытии Issue CEO снимает рабочую метку `status:*`, при переоткрытии ставит актуальную. Уточнения, которые меняют поведение или приоритет, внеси в Issue.

В `<common-dir>/codex-project-team/tasks/` хранятся локальные карточки для технического контекста и передачи работы. Общий Git-каталог доступен через `git rev-parse --path-format=absolute --git-common-dir`. В карточке укажи Issue и PR, worktree, ветку, base/head и SHA кандидата, команды и ссылки на прогоны, ответственного за следующий шаг и условие возобновления. Если карточка и Issue расходятся по требованиям или статусу, используй Issue. Подтверждённые межзадачные решения храни в `decisions.md` с датой и ссылкой на источник.

При возобновлении прочитай Issue и карточку, сверь PR, ветку и прогоны с первоисточниками. Для ожидания запиши конкретное событие, например завершение CI с указанным ID. Используй штатное ожидание по событию, когда оно доступно и входит в поручение.

## Как взять Issue

1. Прочитай открытый Issue и критерии. Проверь исполнителей, метки состояния, последние комментарии и связанные открытые PR, включая Draft. Подтверди GitHub-логин своего пользователя и сверь его с аккаунтом активной авторизации. Для `gh` проверь `gh api user --jq .login`.
2. Если есть чужой исполнитель или открытый PR по той же работе, согласуй передачу с ответственным через Issue перед изменениями. Если это твой начатый Issue, продолжай в существующей ветке и PR. При `status:paused` или `status:blocked` сначала проверь условие возобновления.
3. Если задача свободна, назначь её на подтверждённый аккаунт своего пользователя, поставь `status:in-progress` вместо прежней метки состояния и коротко напиши в Issue, что берёшь в работу. При отказе в назначении, смене статуса или публикации комментария укажи, что удалось и что должен сделать ответственный. До подтверждения назначения и статуса считай начало несогласованным.
4. После назначения перечитай Issue, последние комментарии и открытые PR. Если появился другой исполнитель, конкурирующее сообщение о старте или PR, остановись и согласуй один путь продолжения. Назначение и повторная проверка помогают заметить конфликт. Они не блокируют параллельный старт технически.

## Продуктовая роль и постоянный чат

При явном запросе на новый продуктовый чат создай его штатным способом в том же проекте. Для существующего чата используй указанную пользователем ссылку. Сохрани ссылку или ID и хост в локальном `product-chat.md` рядом с карточками либо в согласованной доступной папке. Привязка локальна и не содержит секретов.

Используй это сообщение для запуска продуктового чата.

> Ты ведёшь продуктовую роль этого Git-проекта. Прочитай `.codex/agents/team_product.toml`, `.codex/project-team/PROJECT.md` и журнал решений, на который ссылается профиль. По Issue и карточке от координатора подготовь критерии либо проверь реализацию. Верни результат в этом чате, чтобы координатор записал критерии в Issue, а результаты проверки связал с PR.

При наличии привязки и разрешения пользователя на отправку используй один и тот же чат для постановки и приёмки, передавай ссылку на Issue, стадию и ссылку на техническую карточку или нужные факты. Считывай вердикт из этого чата штатными инструментами. Если чата, доступа или разрешения на отправку пока нет, используй `team_product` с исходным поручением и журналом решений. Для приёмки по возможности продолжи ту же сессию этого агента. Сохранённые постановки и подтверждённые решения дают следующему запуску контекст. Укажи этот режим в карточке.

## Прохождение задачи и входящего PR

1. **Постановка.** CEO проверяет полноту Issue независимо от настроек обязательных полей формы и назначает команду. Продуктовая роль формулирует наблюдаемые критерии, ограничения и независимый сценарий для рискованного поведения. Содержательные изменения критериев датируй в Issue.
2. **Исполнение и сдача.** Исполнитель работает в отдельной ветке и worktree от проверенной базы. С первым содержательным коммитом открывает Draft PR со ссылкой на Issue. Если ветка или PR уже есть, обновляет их. Для параллельной работы выделяет отдельные тестовые данные, порты и хранилища. Для исправления дефекта проверяет исходное поведение и повторяет проверку после изменения. Когда изменения и проверки готовы, записывает результаты и непроверенное в PR, переводит его из Draft в ready и передаёт на независимое ревью. При остановке оставляет в Issue причину, следующий шаг и ссылку на ветку или PR. Ставит `status:paused` для паузы или `status:blocked` для блокера. Возобновляет работу после выполнения записанного условия, повторной проверки занятости и возврата в `status:in-progress`.
3. **Независимое ревью.** Для каждого PR, включая входящие изменения других участников, CEO сверяет Issue и назначает экспертизу затронутых областей. Оркестраторы запускают субагентов в отдельном контексте с постановкой и точными ревизиями. Авторы и соавторы не принимают собственное изменение. В отчёте фиксируют авторство, проверяющих, применимость строк матрицы и доказательства. Параллельно проверяют полный Server CI для кандидата, с указанием SHA пробного слияния и base/head, если CI тестировал слияние.
4. **Приёмка.** Продуктовая роль сверяет критерии Issue с первичными результатами и независимым сценарием. Эксперты возвращают `READY`, `CHANGES_REQUIRED` или `INCOMPLETE` по [матрице](QUALITY.md). CEO собирает независимые `READY` всех затронутых областей и обоснования неприменимости остальных. При дефекте передаёт исполнителю критерий и способ воспроизведения, при пробеле оставляет проверку открытой с ответственным и следующим шагом. При новом SHA повторяют затронутые проверки и сверяют полный CI на актуальном кандидате.
5. **Слияние.** При итоговом `READY` и актуальном CI сливает только AGaziev или CEO по действующему поручению владельца. Исполнитель передаёт PR на ревью и сам его не сливает. [Активный ruleset](https://github.com/AGaziev/night-horde/rules/27115863) ограничивает изменения `main`, `master` и ветки по умолчанию. Право обхода правил есть у AGaziev.

Запускай роли отдельными агентами. Если интерфейс поддерживает имена проектных агентов, используй профили из `.codex/agents/`. Если доступен только запуск обычного агента, передай инструкции соответствующего профиля отдельным заданием. Отчёт исполнителя приложи после первого независимого прохода. Если независимая роль недоступна, оставь её проверку открытой.
