## Команда агентов проекта

Сначала определи путь изменения по [разграничению продуктовой и служебной работы](.codex/project-team/WORKFLOW.md#продуктовые-и-служебные-изменения). Продуктовые изменения проходят через Issue и PR. Релизы, документация, регламенты и служебная инфраструктура доставляются напрямую в `main` с проверками по риску; отдельный PR не нужен. Перед работой по Issue прочитай его, проверь назначенных исполнителей и связанные открытые PR, включая Draft. Следуй [порядку начала работы и сдачи](.codex/project-team/WORKFLOW.md), [профилю проекта](.codex/project-team/PROJECT.md) и [матрице проверок](.codex/project-team/QUALITY.md).

**Для продуктовых изменений: один Issue — отдельная ветка и отдельный PR.** Не объединяй реализацию нескольких Issues в одной ветке или PR. При обнаружении такого PR проверяющий агент сразу закрывает его без слияния и ожидания ревью, оставляет причину и просит разделить изменения по Issues. Подробности — в [регламенте](.codex/project-team/WORKFLOW.md#один-issue--одна-ветка-и-один-pr).

В ревью отличай серьёзность дефекта от необходимости блокировать слияние по [QUALITY.md](.codex/project-team/QUALITY.md). Неблокирующие подтверждённые замечания — связанные Issues `tech-debt`, совместимые с `READY`. На повторе проверяй исправления и затронутые пути; после двух повторных кругов CEO фиксирует минимальный остаток. Независимость, актуальный CI и существенные проверки остаются обязательными.

Роли постоянных команд описаны в [TEAMS.md](.codex/project-team/TEAMS.md). Без записи в локальном реестре можно выполнить Issue по поручению своего пользователя в роли исполнителя. Полномочия CEO и оркестратора определяются назначением.

## Среды проекта
