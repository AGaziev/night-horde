# Buildcraft — история выбора кандидата и отзыв прежних замеров

Этот документ сохраняет происхождение HP-кандидата `dc92aed82ca58130d039e78947580d713445f778` и исправляет прежнее утверждение о полных забегах. Из 600 JSON-записей на `288f03efc1dbd20bbdfa67a2395fe296a40e2a1c` минимум 32 — незавершённые попытки, ошибочно записанные как поражения. В 450 записях калибровки таких минимум 18. Это консервативная оценка аудита, а не доказательство завершения остальных попыток.

Вывод о соответствии баланса по этим историческим данным: **OPEN**. Старые количества `win=true` ниже не являются полными win rates и не подтверждают достижение ориентиров human 25–40%, smart ≤75%. Их нельзя исправить исключением незавершённых записей из знаменателя: это создаёт смещение по исходам. Итоговая приёмка должна опираться на отдельную серию 10×60 терминальных забегов и сопоставимый baseline с исправленным runner; результаты этой серии координатор хранит отдельно. Этот документ не является итоговой приёмкой.

## Выбранный тогда кандидат

Только `MODES.*.hpMul`, по числу игроков 1 / 2 / 3 / 4+:

| Режим | До | Кандидат |
| --- | --- | --- |
| Полная ночь | 1 / 1 / 1 / 1 | 1,5 / 2 / 2,4 / 2,2 |
| Обед | 1 / 1,13 / 1,13 / 1,13 | 1,9 / 2 / 2,2 / 2,4 |

Множители оружия, наследование DUO, эффекты артефактов, входящий урон врагов, опыт и специальные параметры финала не менялись. Множитель здоровья действует на обычных врагов, боссов и Владыку. Больший HP меняет скорость убийств, получение опыта и возможности эффектов при убийстве; неизменные числа оружия не доказывают сохранение относительной эффективности сильных сборок. Это отдельный предмет проверки кандидата.

## Исторические записанные попытки

На неизменном `288f03e` через `MODE_HP` собраны **450 recorded attempts**, по 30 JSON-записей в 15 ячейках. Плановая длительность режима — 900 секунд «Ночи» или 600 секунд «Обеда»; достижение терминального состояния старый runner не проверял. Проба A: ночь `1.4,1.8,1.8,2`, обед `1.9,2,2.2,2.4`. Проба B: только ночь `1.5,2,2.4,2.4`. Других HP-вариантов на этапе выбора не запускали.

`*` При первоначальном выборе у ночной четвёрки было 4 флага `win=true` из 30 попыток с ×2,4 HP против 14 с ×2. Выбрана середина ×2,2. Эту точку на этапе выбора отдельно **не измеряли**; старые количества не доказывают её пригодность.

Аудит обнаружил следующие однозначно незавершённые записи (censored attempts):

| Серия / ячейка | Незавершённых минимум |
| --- | ---: |
| A / human соло Ночь | 7 / 30 |
| A / smart соло Ночь | 1 / 30 |
| A / human соло Обед | 1 / 30 |
| B / human соло Ночь | 8 / 30 |
| B / smart соло Ночь | 1 / 30 |
| Вся калибровка | 18 / 450 |
| Без калибровки: human соло Ночь / Обед, smart соло Ночь | 21 / 60, 9 / 60, 2 / 60 (всего 32 / 600) |

Причина: алтарный `swap` требует ID заменяемого артефакта `drop`, а runner отправлял только индекс карты. Отклонённое предложение оставалось открытым и замораживало соло; фиксированный лимит итераций истекал, после чего `runLog.build(r, false)` создавал ложное поражение. Нулевой счётчик очевидных незавершений у группы не подтверждает корректность её траектории: отклонённый обмен мог блокировать дальнейшие предложения конкретного героя. Поэтому кооперативные ячейки тоже требуют новых данных после исправления протокола.

Старые проценты и примеры интервалов Wilson отозваны как доказательство баланса. Группы 5–8 на этапе выбора отдельно не проверялись и используют последний элемент массива HP. Даже корректные новые симуляции оценивают поведение этих ботов, а не гарантируют вероятность побед живых игроков.

## Исправленный протокол измерения

Старый runner: `pm/run-sim.mjs` из `ffdb202f1a142e1e1bb6d7e7f3e9079395020544`, совпадающий с `288f03e`, SHA-256 `ff7b9ef81f69f2d87849e5fa7dfcbd96ac899d4d46a71b42faed99b7cb563f5d`. Первичные JSON и команды сохранены без перезаписи: `functional-288f03e`, `calibration-a-night`, `calibration-a-lunch`, `calibration-b-night`, `calibration-summary.json`. Доказательства отзыва — независимые `calibration-completion-audit.json`, `calibration-review-dc92aed.md` и `legacy-baseline-completion-audit.json` у координатора. Аудит также нашёл незавершённые попытки в прежних baseline; сравниваемые версии нужно запускать одним исправленным runner.

Исправление runner — `d2dee89d50295b750c75513809dfcc001975384e`. Тела `chooseHuman`, `choose`, `chooseBan` и движения сохранены побайтно. Для обмена добавлен первый доступный `replace[0].id` — технический выбор из реального UI без оптимизации сборки; все действия используют текущий `offerEpoch`, если он есть. Это исправляет приём предложений и меняет прежние ошибочные траектории, поэтому старые результаты нельзя объявлять эквивалентными новой политике исполнения.

Runner учитывает только `state === 'over'` с настоящим `lastLog` после вызова `Room.finish`. Лимит итераций служит защитой от зависания; при незавершении CLI падает с диагностикой и не создаёт запись о поражении. Рядом с неизменным массивом `logs` выводится массив `completion`, по одной записи `{k, terminal: true, state: 'over', time, runLength, win, logId, iterations, finishCalls}` на забег. Проверка серии должна сверять длину массивов, `finishCalls >= 1`, состояние, ID, исход и длительность с соответствующим логом.

Среда прежних попыток — Node.js `v24.22.2`. Для новых сравнений сохраняются ротация героев, `K0=0` и один непрерывный LCG на ячейку: `x=(1664525*x+1013904223)>>>0`, `Math.random=x/4294967296`; seed human `4871`, smart `9137`. Seed не подбираются. Потоки расходуются по-разному после изменения параметров и исправления обработки предложений; это не парное сравнение отдельных забегов.

Пример новой серии с закреплёнными APP и исправленным runner:

```sh
APP=/path/to/pinned-candidate/app MODE=night SIM_SEED=4871 K0=0 \
node --import /path/to/seed-rng.mjs /path/to/pinned-fixed-runner/pm/run-sim.mjs 1 60 human 900
```

Тело preload:

```js
let seed = Number(process.env.SIM_SEED) >>> 0;
Math.random = () => {
  seed = (Math.imul(seed, 1664525) + 1013904223) >>> 0;
  return seed / 4294967296;
};
```

Прежние попытки выполнялись максимум четырьмя процессами, без параллельных тестов с измерением производительности. Наличие полного JSON-массива само по себе не является доказательством 60 терминальных забегов.
