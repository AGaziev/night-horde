# Где хранить прогресс игроков (T1) — разбор, 2026-11-10

Сейчас: диск VM Black Hole стирается при каждом деплое, прогресс только в localStorage браузера.

## Что выяснено (доки Vibecode + проверка нашим ключом)

- Наш ключ — `oauth_app` (ключ приложения «Vampire Survivors Online»), портал `bitrix24.team`, тариф коммерческий (ENT).
  Скоупы есть: `disk`, `entity`, `user`, `vibe:storage` и др.
- Gateway уже присылает серверу игры личность игрока: `X-Vibe-User-Id`, `X-Vibe-User-Name` (имя мы уже берём,
  `server.js:59`). Для вызовов от имени игрока — `X-Vibe-Authorization: Bearer vibe_session_*` (живёт 24 ч).
  Приходит ли он к нам сейчас — не проверено.
- Произвольного вызова REST Битрикс24 нет: «All methods have dedicated wrappers — no /v1/call». `entity.*`
  и `app.option.*` портала как хранилище «ключ-значение» не обёрнуты.

### Вариант А — диск портала (Битрикс24 Диск)
- Обёртки `/v1/disk/*`, `/v1/files`, `/v1/folders`, `/v1/storages`; запись в два шага (reserve → upload).
- Работает только от имени конкретного пользователя: наш ключ без сессии игрока отвечает
  `TOKEN_MISSING` на `GET /v1/disk/capabilities` (проверено).
- Значит, файл прогресса лежит на личном Диске каждого игрока: игрок его видит, может удалить или поправить
  руками (накрутка), это мусор на чужом Диске. Общая таблица рекордов требует общей папки с правами на запись
  для всех — права через REST не отзываются.
- Нужен проброс `X-Vibe-Authorization` и передача ключа приложения в runtime (`env`), сейчас его там нет.

### Вариант Б — хранилище приложения Vibecode (`/v1/storage`, S3)
- Изолировано по приложению; ключ приложения без сессии игрока пишет в общее пространство приложения
  (проверено: `GET /v1/storage/objects` отвечает, пусто).
- Не зависит от деплоя, не лежит на Диске сотрудников, игрок не может руками поправить файл.
- Прямая загрузка до 10 МБ одним запросом; цена ~2,2 «вайба» за ГБ в месяц — наши JSON по килобайту ничтожны.
- Ключ игрока = `X-Vibe-User-Id` (только цифры — проверять, как велят доки), файлы `players/<id>.json`,
  общий `leaderboard/week-<n>.json`.

## Рекомендация
Б. Сервер держит прогресс в памяти, читает файл игрока при входе в лобби, пишет в конце забега и раз в N минут.
Ключ приложения передаём в runtime через `env` при деплое (не в репозиторий). При недоступности хранилища —
игра работает, как сейчас, на localStorage.

Открывает: M1 мастерская углей, M3 луны, B2 недельная таблица, корона и рекорды «Ночи дня» на сервере, общие
для всех устройств игрока.

## Что проверить до реализации
1. Приходит ли `X-Vibe-User-Id` числом у игроков портала (у гостей — с префиксом, им только localStorage).
2. Запись и чтение объекта ключом приложения из runtime (тестовый объект, затем удалить).
3. Задержка записи из Black Hole и поведение при `409 STORAGE_KEY_CONFLICT`.

## Результаты проверки (v22, 2026-11-10)

Скрипт `pm/storage-probe/probe.mjs` (ключ из `.env`, в вывод не попадает), запуск с Мака, не из Black Hole; сырые ответы —
`pm/storage-probe/run1.json`.

1. **Запись → чтение → удаление ключом приложения** работают. Загрузка — `POST /v1/storage/objects/upload` (путь A, форма),
   ответ 200 с `uploadStatus: COMPLETED`. Чтение — `GET /v1/storage/objects/<key>` → 302 на предподписанную ссылку
   Yandex Object Storage; ссылку читаем отдельным запросом без `X-Api-Key`. Нет объекта — `404 STORAGE_OBJECT_NOT_FOUND`.
2. **Удаление мягкое:** `DELETE` → 200, дальше чтение отвечает `410 STORAGE_OBJECT_DELETED`, список по префиксу объект
   уже не показывает, данные платформа хранит ещё 30 суток. Повторная загрузка того же ключа «оживляет» объект с тем же `id`.
   Для игры 410 = «объекта нет».
3. **Замена:** повторная загрузка по тому же ключу заменяет содержимое (тот же `id`, новый `sha256`), чтение сразу отдаёт
   новое.
4. **Задержка (с Мака):** запись 200–780 мс (первая 730 мс), чтение с переходом по ссылке 130–400 мс. Из Black Hole не
   замерено. Для игры несущественно: чтение при входе в меню, запись в фоне.
5. **Конкурентная запись и `409 STORAGE_KEY_CONFLICT`:** 5 одновременных загрузок в один ключ — все 200 (платформа ставит
   их в очередь, ответы 0,14–2,4 с), 409 не получили. По документации 409 приходит, если запрос прождал очередь дольше 60 с;
   повторять надо весь запрос. **Порядок не гарантирован:** после пяти параллельных записей осталась третья, а не последняя.
   Поэтому сервер игры сам пишет один объект строго по одному запросу за раз.
6. **`X-Vibe-User-Id` числом у игроков портала** — по документации да (цифры = пользователь портала, `net_…`, `share:…`,
   `vibe:…` — без ID в портале). На живом шлюзе не проверено; код хранит прогресс только для чисто числовых id.

Тестовые объекты (`probe/…`, `selftest-v22/…`) удалены (мягко).
