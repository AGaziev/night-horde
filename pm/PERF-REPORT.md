# Ночная орда — аудит производительности

Дата: 2026-11-06. Код игры не менялся. Стенды и скрипты — в `../perf-lab/`.
Строки указаны по `app/` на 22:10; другая сессия параллельно правит те же файлы, поэтому номера могут сдвинуться.

## Коротко

- **Сервер не узкое место.** Тик в поздней игре (8 игроков, 350 врагов, у каждого эволюция + 2 связки + оружие 5 ур.) занимает 0,27 мс в среднем и 0,4 мс p95 при бюджете 33 мс — меньше 1 % одного ядра. Сборка снимка — 0,06 мс. Ускорять CPU сервера сейчас незачем.
- **Главная нагрузка — трафик и растеризация на клиенте.** Снимок весит 13–16 КБ, это **~134 КБ/с на клиента** (≈ 1,1 Мбит/с; ≈ 120 МБ за 15-минутный забег на телефоне). На комнату из 8 человек сервер отдаёт ≈ 1,1 МБ/с.
- **Кадр на M5:** JS-часть `renderer.draw` — 2,0–2,7 мс p50 и 5,8–6,5 мс p95; вместе с растеризацией на GPU ≈ 7 мс. При программной растеризации (так рисуют слабые ноутбуки без GPU-ускорения canvas) — **≈ 66 мс на кадр**, т. е. ~15 к/с. Из них виньетка — 28 %, враги — 17 %, а DPR 2 против 1 удваивает всё.
- HUD (`ui.updateHud`) — 0,003–0,2 мс, DOM пишется только при изменении значения. Не проблема.

## Как мерили

| Что | Чем | Условия |
|---|---|---|
| Тик сервера, фазы, GC | `perf-lab/stress.mjs`, `phases.mjs`, `--cpu-prof`, `--trace-gc` | Room напрямую, 8 ботов ходят по кругу и берут первую карту, t = 700 с, 60 с симуляции, зафиксированный `Math.random` |
| Трафик | `perf-lab/bytes.mjs`, `enc.mjs` | тот же сценарий, байты JSON по полям, deflate уровня 1 |
| Клиент | `perf-lab/live` (копия игры + 7 серверных ботов вокруг человека, `PERF_STRESS=1 PORT=3556`), встроенный браузер, 1440×900 @2x | панель была скрыта, кадры прокручивались вручную; таймеры методов через обёртки прототипа; ablation — отключение слоя и сравнение |

Оговорки:
- Машина была сильно загружена (load average 16–31 на 10 ядрах). Отдельные «тики» по 200–400 мс в первых прогонах — вытеснение процесса ОС, а не код: они попадали в произвольные фазы (`rebuildGrid` 181 мс и т. п.) и исчезли при меньшей нагрузке. Сравнение мелких серверных правок по времени стены поэтому ненадёжно; доли фаз взяты из CPU-профиля.
- GPU-стоимость кадра измерена один раз (30 кадров + одно чтение пикселя). После нескольких `getImageData` Chrome переводит canvas на программную растеризацию — этим и воспользовались для замера «слабой машины». Абсолютные цифры программного режима — оценка худшего случая, относительные доли — надёжны.
- Реальные слабые устройства и троттлинг CPU не проверялись (нет CDP-троттлинга в этом браузере). Web Audio в скрытой панели не запускается — звук оценён только по коду.

## Топ узких мест (по убыванию эффекта)

### 1. Виньетка — радиальный градиент на весь экран каждый кадр
- **Где:** `public/js/render.js:148` (`ctx.fillStyle = this.vignette; ctx.fillRect(0, 0, w, h)`), так же вспышка урона `render.js:160` (`hurtGrad`).
- **Замер:** программная растеризация 2880×1800: 66 → 47,6 мс без виньетки (**−28 %**); при 1440×900 виньетка одна стоит 5 мс. На GPU это заливка 5,2 Мпикс с градиентом каждый кадр — заметно на встроенной графике.
- **Исправление:** вынести виньетку и вспышку урона из canvas в CSS-слой поверх него (`div` с `radial-gradient`, `pointer-events: none`; вспышка — `opacity` того же или второго слоя). Композитор браузера рисует такой слой почти бесплатно. Запасной вариант — отрисовать градиент один раз в маленький offscreen-canvas (¼ размера) при `resize` и класть `drawImage` с масштабом.
- **Выигрыш:** до четверти кадра на слабых машинах; на M5 ~1 мс GPU.
- **Трудоёмкость / риск:** 20–30 мин / низкий (визуально идентично; проверить, что HUD и меню лежат выше слоя).

### 2. Нет адаптивного разрешения: DPR 2 на любом устройстве
- **Где:** `render.js:77` — `this.dpr = Math.min(2, devicePixelRatio)`.
- **Замер:** программная растеризация: DPR 1 → 29 мс, 1,5 → 45 мс, 2 → 66 мс. Цена кадра почти линейна по числу пикселей.
- **Исправление:** адаптивный DPR: держать скользящее среднее времени кадра (из `rAF`), при > 20 мс несколько секунд подряд понижать DPR ступенями 2 → 1,5 → 1,25 → 1, при запасе — возвращать. Отдельно: на тач-устройствах стартовать с 1,5. Плюс ручной переключатель «Качество» в настройках звука/игры.
- **Выигрыш:** ×1,5–2,3 по растеризации там, где она узкое место; на сильных машинах ничего не меняется.
- **Трудоёмкость / риск:** 1–2 ч / низкий (`resize()` уже пересоздаёт градиенты; следить, чтобы не «прыгало» — гистерезис).

### 3. Трафик снимков: враги — 55 % байт, всё в текстовом JSON без сжатия
- **Где:** `server/game.js:2866` (строка врага `[id, type, x, y, hp%, state]`), `server/game.js:188` (`broadcast` → `JSON.stringify`), `server/server.js:267` (`perMessageDeflate: false`).
- **Замер (на клиента, поздняя игра):** 130–134 КБ/с. По полям: `e` 71 КБ/с, `fx` 24 КБ/с (из них `hit` 8,7, `shot` 6,5, `pend` 4,0, `zap` 2,2), `g` 10, `p` 9,7, `z` 9,2, `tr` 3,5.
  Альтернативы для поля `e` (КБ/с): как сейчас 71; id как разница с предыдущим 64; **дельта к прошлому снимку (для известных врагов только `idΔ, dx, dy`, hp/state — при изменении) 31**; бинарная строка 9 байт ≈ 31.
  Весь снимок: сейчас 130; с deflate 55; с дельтой врагов и deflate 34.
- **Исправление (по шагам):**
  1. Дельта-кодирование врагов относительно последнего снимка, который клиент точно получил (или ключевой снимок раз в 1 с + дельты; при пропуске клиент просит полный). Клиент уже хранит `eIdx` по id — восстановление дешёвое.
  2. Не включать `permessage-deflate` в лоб: deflate снимка стоит ~0,8 мс, а `ws` сжимает **для каждого сокета отдельно** — 8 × 0,8 мс × 10 Гц ≈ 6 % ядра, больше, чем вся симуляция. Если сжимать — один раз на комнату (готовый буфер, `ws.send(buf, { binary: true })` и `DecompressionStream` на клиенте) и только после проверки, что туннель платформы это пропускает.
  3. Интерес по игроку: сейчас каждому уходят враги, видимые хоть кому-то (`game.js:2851` — объединение обзоров). При разбежавшихся игроках отдельный список на клиента сокращает `e` кратно, но требует отдельной сериализации на клиента (+0,1 мс × 8) — делать после дельты.
- **Выигрыш:** −45…−75 % трафика (до ~35 КБ/с), меньше разбора JSON на телефоне, меньше расход мобильного интернета (120 → ~35 МБ за забег).
- **Трудоёмкость / риск:** дельта — 3–5 ч / средний (синхронизация при потере снимка, переподключение, SSE-транспорт; нужны тесты в `sim-test.js` и проверка рассинхрона). Сжатие — 1–2 ч / средний (поведение прокси платформы).

### 4. Отрисовка толпы врагов векторными путями
- **Где:** `render.js:417` `drawEnemies` → `drawBats/Ghouls/Skels/...`, `drawStates` (`render.js:577`).
- **Замер:** JS 1,3 мс из 2,7 мс кадра (≈ 50 %); в программной растеризации отключение врагов даёт −11 мс (−17 %), отметок состояний — до −7 мс. За кадр с 350 врагами: 1 671 `arc`, 657 `ellipse`, 3 000 `moveTo`, 2 294 `lineTo`, 807 `fill`, 281 `stroke`, 872 смены `fillStyle`. Пакетирование по типам уже сделано хорошо.
- **Исправление:** заранее растеризовать спрайты врагов (тип × 4–8 фаз анимации × направление, плюс варианты «заморожен/замедлен/горит») в атлас offscreen-canvas с учётом DPR и рисовать `drawImage`. Тени — одним спрайтом. Полоски HP оставить путями.
- **Выигрыш:** по опыту такого перехода — кратное снижение JS и растеризации врагов (оценка: −1 мс JS на M5, −8…−10 мс в программном режиме). Не замерено — нужен прототип.
- **Трудоёмкость / риск:** 4–6 ч / средний (анимации, привязанные к `now` и `id`, надо свести к фазам; элиты масштабируются — отдельный размер или `drawImage` с масштабом).

### 5. Серверная сетка соседей: две перестройки за тик и ключи-не-Smi
- **Где:** `server/game.js:787` (`moveEnemies` перестраивает сетку) и `game.js:657` (`tick` перестраивает ещё раз); `Grid.key` `game.js:106` — ключ до 4,3·10⁹, вне диапазона малых целых V8, каждый `Map.get` работает с числом в куче.
- **Замер (CPU-профиль, 120 с поздней игры):** `moveEnemies` 19,7 % собственного времени, `Grid.query` 19,0 %, `rebuildGrid` 5,6 % + `clear` 2,7 % + `insert` 2,0 %. ~490 запросов к сетке за тик, в среднем 8,8 ячейки и 6,2 сущности на запрос.
- **Исправление:** (а) ключ в диапазоне Smi: `(cx + 16384) * 32768 + (cy + 16384)` с клампом ±16000 — однострочник; (б) первая перестройка в `moveEnemies` не нужна, если использовать сетку с конца прошлого тика (позиции устарели на один шаг ≤ 4 px, радиус запроса это покрывает; новые враги появятся в сетке со следующего тика); (в) дальше — плоская сетка на типизированных массивах (сортировка подсчётом) вместо `Map` массивов.
- **Выигрыш:** по профилю — до 20–30 % времени тика. В абсолюте это 0,05–0,1 мс: **делать только если число комнат на одном процессе вырастет** или поднимется лимит врагов.
- **Трудоёмкость / риск:** (а)+(б) 20 мин / низкий; (в) 2 ч / низкий-средний.

### 6. Невидимые лужи ледяного следа опрашивают сетку каждый тик
- **Где:** `server/game.js:2541` `iceTrail` создаёт скрытые лужи, `game.js:2684` → `slowInPuddle` (`game.js:2710`) на каждую лужу каждый тик.
- **Замер:** в поздней игре в среднем 139 луж, из них 89 скрытых; `updatePuddles` — 10 % времени тика по фазам, 5,5 % по профилю.
- **Исправление:** замедление из луж применять раз в 3 тика (держать `SLOW_HOLD` ≥ 0,1 с — он и так 0,1 с) или сливать соседние точки следа в одну капсулу/отрезок.
- **Выигрыш:** −5…−7 % тика. В абсолюте мало (см. п. 5).
- **Трудоёмкость / риск:** 20 мин / низкий (проверить, что замедление не «мигает»).

### 7. Мелкие аллокации в горячем цикле сервера
- **Где / что:**
  - `updateTimers` (`game.js:2162`): два `filter` на каждом тике с таймерами — новый массив каждый тик.
  - `nearestEnemies` (`game.js:1559`): линейный проход по всем 350 врагам × `count` + `picked.includes`; зовётся ~40 раз в секунду (молнии, ножи, наведение снарядов при смерти цели — `ptgt`). 1,3–1,4 % тика.
  - `explode` (`game.js:1320`): `this.grid.query(..., [])` — новый массив на взрыв.
  - `snapshot` (`game.js:2849`): замыкание `visible` и `[...this.heroes.values()]` на каждый снимок, `visible` проходит по всем игрокам для каждого врага/кристалла.
- **Замер:** GC на сервере — ~2,3 малых сборки в секунду по 0,5–1,4 мс, одна полная за минуту ≈ 1,2 мс; суммарно < 0,5 % времени. Не влияет на тик заметно.
- **Исправление:** заменить `filter` на компактирование на месте; `nearestEnemies` — через сетку с расширяющимся радиусом; переиспользовать буфер в `explode`.
- **Выигрыш:** незначительный; приводить в порядок попутно.
- **Трудоёмкость / риск:** 30–40 мин / низкий.

### 8. Цифры урона и частицы — текст и мелкие заливки
- **Где:** `render.js:2256` (цифры: `strokeText` + `fillText` на каждую, у критов ещё `save/translate/scale/restore`), `render.js:2248` (частицы: `fillStyle` + `globalAlpha` + `fillRect` на каждую); `game.js:539` — криты обходят лимит `MAX_NUMBERS`.
- **Замер:** в поздней игре 100–150 цифр (при лимите 90 — из-за критов) и 550–650 частиц. JS: `drawEffects` 0,73 мс, без цифр 0,35 мс, без частиц 0,46 мс. В программной растеризации разница в пределах шума.
- **Исправление:** кэшировать цифры в спрайты (атлас цифр 0–9 и «!» с обводкой) и рисовать `drawImage`; не рисовать цифры и частицы вне экрана; общий лимит, включая криты (например, 30 крит + 90 обычных); частицы группировать по цвету и квантованной прозрачности в один путь.
- **Выигрыш:** −0,3…−0,5 мс JS на кадр (≈ 15 % JS-кадра на M5, в 3–5 раз больше на слабом ноутбуке).
- **Трудоёмкость / риск:** лимит и отсечение по экрану — 15 мин / низкий; атлас — 1–2 ч / низкий.

### 9. Звук: свёрточный ревербератор 2,4 с на общей шине
- **Где:** `public/js/audio.js:145` (`this.verb.buffer = this.impulse(2.4)`, стерео).
- **Замер:** не измерено (в скрытой панели аудиоконтекст не стартует). Голоса ограничены (`MAX_VOICES = 32`, лимиты частоты по звукам), утечек узлов в коде не видно: источники останавливаются по `stop()`, gain-узлы отцепляются сборщиком.
- **Исправление:** на телефонах/при пониженном качестве — короткий импульс (0,8–1 с) или моно; проверить в Performance-панели Chrome на реальном телефоне.
- **Трудоёмкость / риск:** 15 мин / низкий; проверка — вручную.

## Что не проверено

- Реальные слабые ноутбук и телефон (оценки по программной растеризации и пропорциям).
- GPU-стоимость отдельных слоёв (только кадр целиком ≈ 7 мс на M5).
- Поведение туннеля платформы со сжатием WebSocket.
- Звук под нагрузкой.
- Цифры GC клиента: `performance.memory` в Chrome грубый — видно ≈ 3,6 заметных сборки в секунду и десятки КБ на кадр, но они идут от путей canvas внутри движка, а не от JS-объектов игры; `game.update` в JS-куче почти не мусорит.
