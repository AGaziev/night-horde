# v22 — прогресс игрока на сервере (хранилище Вайбкода)

Код в `app/` (GAME_VERSION `v22`, PROTO 19), база — `app-v21-base/`. **Не выложено.**

## Что сделано

- **`server/storage.js`** — хранилище приложения Вайбкода (`/v1/storage`), ключ из `process.env.VIBE_APP_KEY`.
  Кэш в памяти, чтение при входе (`/api/session`), запись по таймеру пачками: игрок не чаще раза в 15 с, таблица недели —
  в 30 с, до 8 записей за такт, один объект — строго один запрос за раз. Повторы после ошибок с паузой 5 с … 5 мин.
  На SIGTERM/SIGINT несохранённое уходит сразу (до 5 с). Версия схемы `schema: 1` в каждом файле.
- **Кто хранится:** только числовой `X-Vibe-User-Id`. Гости (`share:…`), `net_…`, `vibe:…`, нет заголовка — как раньше,
  `localStorage`.
- **Что хранится** (`players/<id>.json`): счётчики достижений `ach` (`wins, knightBest, revives, knifeKills, bosses, lords` —
  из них открываются герои, `lords` — корона за Владыку), известные связки `duos`, `migrated`, `runs`, `updatedAt`.
  Эволюций и отдельных «рекордов финала» в `localStorage` не было — переносить нечего. Настройки (звук, имя, герой, режим)
  остались в браузере.
- **Перенос:** первый `prog` с `mig: false` → клиент один раз шлёт `mig` со своими `nh.ach`/`nh.duos`; сервер проверяет
  (целые ≥ 0, потолки, `knightBest` ≤ 15:00, `lords` ≤ `wins`, связки только из `DUOS`) и объединяет в пользу большего.
  Дальше источник правды — сервер; повторный перенос игнорируется.
- **Забег:** счётчики по-прежнему считает сервер; в конце забега они прибавляются к объекту игрока, итог уходит в
  `over.stats[].tot`, клиент берёт его вместо своего сложения. Открытых героев игрока портала сервер берёт из своих данных
  (список от клиента заменяется).
- **Рекорды недели** `leaderboard/week-<YYYY-Www>.json`: лучший забег каждого игрока портала (Владыка > победа > поражение,
  затем время, затем убийства), герой, режим, размер отряда. Блок «Рекорды недели» в меню — топ-10, своя строка подсвечена.
  Таблица пишется только после успешного чтения недели.
- **Наблюдаемость:** `/api/busy` → добавлено только `storage: true|false`. Ошибки — строки `[storage] … failed: <код>
  (errors: read N, write M)` в журнале.
- Протокол: новые сообщения `prog`, `top` (сервер → клиент), `mig`, `top` (клиент → сервер), поле `tot` в `over` — PROTO 18 → 19,
  открытые вкладки v21 после выкладки перезагрузятся сами.
- Для локальной проверки — `HORDE_STORAGE_PREFIX=selftest-…/` (объекты под префиксом). Всё описано в `app/DESIGN.md`,
  раздел «Прогресс на сервере (v22)»; результаты проверки хранилища — в `pm/STORAGE-options.md`.

## Проверки

- **Хранилище ключом из `.env`** (`pm/storage-probe/probe.mjs`): запись/чтение/замена/удаление работают; запись
  0,2–0,8 с, чтение 0,13–0,4 с (с Мака); 5 параллельных записей в один ключ — все 200, 409 не получили, но порядок
  не гарантирован (победила 3-я) → сервер сериализует запись сам. Удаление мягкое (410, 30 суток).
- **Тесты:** все 8 файлов `server/*-test.js` зелёные. Новый `server/v22-test.js` (хранилище — заглушка): id портала и
  гости, ISO-недели (включая 53-ю и переход года), проверка присланных значений, слияние localStorage с серверными данными,
  перенос один раз, новый игрок (404), отказ хранилища (чтение и запись, повтор, неперезапись непрочитанного, забег в
  очереди), без ключа, конкурентная запись (5 изменений → 1 запись, одна запись за раз, интервал), общий кэш двух сессий и
  его освобождение, схема новее, рекорды недели (лучший результат, топ-10, `me`, неизвестный герой, новая неделя, сбой
  чтения недели), хук конца забега в `Room` (`tot` только у игрока портала, сломанный хук не ломает итоги), настоящий
  клиент хранилища на подменённом `fetch` (404/410/302 без ключа на ссылке/409).
  Поправлены старые проверки: версия/протокол в `v20-test.js`, `finale-test.js`; ответ `/api/busy` в `sim-test.js`.
- **`sim-test.js` нестабилен на замере «tick under 3 ms»** при нагрузке машины (load ~29): в чередующемся прогоне падали и
  v22 (2 из 5), и база v21 (3 из 5). К правкам не относится; при спокойной машине проходит.
- **Ручной прогон локального сервера с настоящим ключом** (префикс `selftest-v22/`, игроки `999999999` и `999999998`):
  перенос (`lords: 7` при `wins: 1` урезан до 1, `knightBest: 99999` → 900, неизвестная связка отброшена), забег (`tot`
  wins 1 → 2), рекорды недели, гость `share:…` → `srv: false`, `/api/busy` → `storage: true`. После SIGTERM в хранилище
  лежали правильные объекты; после перезапуска новая сессия получила сохранённый прогресс (первый `prog` ~0,5 с).
  Тестовые объекты удалены, список по префиксу пуст.
- **Браузер локально, без звука** (встроенный браузер, тестовый id подставлял скрипт-обёртка `pm/storage-probe/v22-server.mjs`):
  перенос из `localStorage` → герои и корона из серверных данных; забег → победа засчитана сервером, своя строка в рекордах;
  очистка `localStorage` + перезагрузка → прогресс вернулся с сервера; неверный ключ → игра на `localStorage`, «Рекорды
  недели сейчас недоступны», ошибки в журнале; без ключа → как v21, блока рекордов нет. 375 px — без горизонтальной
  прокрутки. Кадры: `pm/shots-v22/`.

## Что не проверено

- Работа из Black Hole на проде: задержка, приходит ли `X-Vibe-User-Id` числом у игроков портала на живом шлюзе.
- Настоящий 409 от хранилища (не воспроизвёлся; обрабатывается как обычная ошибка записи с повтором).
- Сброс на SIGTERM при деплое на проде (локально работает; сколько платформа ждёт после SIGTERM — неизвестно).
- Перенос из второго браузера того же игрока: принимается только первый перенос, прогресс второго браузера не сольётся.
- `?unlockall=1` для игрока портала на проде больше не открывает героев (сервер берёт список из своих данных).
- `over.stats[].tot` видят все участники забега (счётчики достижений соседей, без личных данных).

## Переменные окружения на проде

- `VIBE_APP_KEY` — ключ приложения со скоупом `vibe:storage` (тот же, что `VIBE_KEY` в `.env`). Без него хранилище
  выключено, игра работает как v21.
- `HORDE_STORAGE_PREFIX` — **не задавать** (только для локальных проверок).
